======================================
任务随机发布器 - 系统设计与构思
======================================

一、项目简介
======================================

任务随机发布器是一个帮助用户解决动力问题的任务管理工具。通过游戏化的"抽卡"机制，
将任务随机推送给用户，减少决策疲劳，让用户无需思考"现在该做什么"，
直接执行系统分配的任务。


1.1 目标用户画像
--------------------------------------

本系统的目标用户是：
- 想要自律但缺乏动力的长期理想追求者
- 相对成熟，不是自欺欺人或纯粹不想做的人
- 需要一个系统来打破"想做什么就做什么"的短期诱惑循环
- 需要减少决策疲劳，让任务分配自动化

2.3 核心设计理念
--------------------------------------

1. 游戏化抽卡机制 - 用"抽卡"代替任务选择，增加仪式感和趣味性

4. 标签分类系统 - 支持多标签、多条件筛选
5. AI智能辅助 - 支持自然语言批量创建任务

五、设计原则
======================================

5.1 核心原则
--------------------------------------

1. 减少决策疲劳 - 用户不需要思考"现在该做什么"
2. 时间即货币 - 可用时间决定任务选择范围
3. 游戏化体验 - 抽卡机制增加趣味性
4. 数据驱动 - 记录所有行为用于后续分析
5. 用户自主 - 保留拒绝和调整的权限


5.2 用户交互原则
--------------------------------------

1. 简洁优先 - 界面元素尽量少
2. 即时反馈 - 每个操作都有明确反馈
3. 可逆操作 - 关键操作支持撤销
4. 渐进披露 - 高级功能逐步展示


5.3 换牌规则
--------------------------------------

基于用户画像——"不是自欺欺人的人，但需要防止无意识滑向逃避"——系统给予有限弹性。

触发条件：仅在单抽模式下可用，五连抽不可换牌（五连抽本身就是给选择权的）。

流程：
1. 用户抽到任务A，卡面展示
2. 卡片下方出现"开始任务"和"换一个"两个按钮
3. 点击"换一个"：
   - 弹出简短理由选择框：精力不足 / 时间不够 / 刚做过类似任务 / 其他
   - 用户选择后，任务A权重暂时归零（本次抽卡会话内），重新抽取任务B
   - 任务B展示，按钮变为"开始任务"和"接受任务"，没有"换一个"了
4. 拒绝理由写入 task_rejection_log

防滥用：
- 每次打开抽卡界面，换牌机会只有1次。关闭再打开不重置
- 不记录换牌历史，仅记录拒绝理由

不同任务类型区别对待：
- deadline_progressive的子任务：换牌后15分钟内必须再次抽取，超时自动恢复任务A
  这条规则的设计意图：子任务之间有依赖关系，临时逃避不解决根本问题，
  系统给你15分钟缓冲，但最终还是要面对
- deadline_flexible：在ddl > 3天时允许换牌；ddl <= 3天（进入危险区）不允许换牌
  危险区内的拒绝视为"硬拒绝"，计入后续诊断分析
- daily_habit/weekly_routine：不参与随机池，不受此规则影响


六、加权随机算法（核心）
======================================

6.1 算法设计
--------------------------------------

加权随机是本系统的核心机制，通过多维度权重计算决定任务抽取概率。


6.2 权重计算因子
--------------------------------------

因子            权重范围    说明
DDL紧急度       1.0-3.0    距离截止日期越近，权重越高
能量匹配度      0.5-2.0    根据用户当前能量与任务需求匹配
时间段匹配      0.8-1.5    任务偏好时间与当前时间匹配度
历史成功率      0.5-2.0    用户历史上完成该类任务的成功率
阻力等级        0.3-1.5    低阻力任务权重更高
优先级          1.0-2.0    用户设定的优先级
任务新鲜度      0.8-1.2    长时间未抽取的任务权重略高
任务阻力修正    0.5-1.5    历史阻力高的任务降权，低阻力的升权
日间时段匹配    0.7-1.3    结合 user_state 中的时段能量数据调整
连续完成激励    1.0-1.3    连续完成同类任务后，同类短暂升权（正向惯性）


6.3 算法公式
--------------------------------------

最终权重 = 基础权重 × DDL紧急度 × 能量匹配度 × 时间段匹配 × 历史成功率 × 阻力系数 × 优先级 × 新鲜度 × 任务阻力修正 × 日间时段匹配 × 连续完成激励 × 冷却因子


6.4 算法流程
--------------------------------------

def weighted_random_selection(tasks, user_state, session_context):
    # 1. 过滤不可用任务（未到时间、已在弃牌堆等）
    available_tasks = [t for t in tasks if is_available(t, user_state)]

    # 2. 计算每个任务的权重，含 task_profile 策略权重
    weights = []
    for task in available_tasks:
        # 基础权重 * 各因子
        weight = calculate_base_weight(task, user_state)

        # task_profile 策略权重修正（见14.4节）
        weight *= calculate_profile_weight(task)

        # 冷却衰减（见6.5节）
        weight *= calculate_cooldown_factor(task, session_context)

        weights.append(weight)

    # 3. 加权随机选择
    selected = random.choices(available_tasks, weights=weights, k=1)[0]
    return selected


6.5 冷却机制
--------------------------------------

问题：加权随机公式中，每个任务的权重独立计算，未考虑刚才抽到过什么。
连续抽到同一科目或同一类型任务会引发用户抗拒。

方案：多级冷却衰减

在现有加权随机流程的步骤2（计算权重）之后，步骤3（随机选择）之前，插入冷却处理：

def calculate_cooldown_factor(task, session_context):
    factor = 1.0

    # 同一任务连续出现 -> 移出候选池
    if task.id == session_context.last_drawn_task_id:
        return 0

    # 同一类别（科目）连续出现 -> 大幅降权
    if task.category == session_context.last_drawn_category:
        factor *= 0.3

    # 同一类别在最近3抽中出现过2次 -> 中度降权
    if session_context.category_count_in_last_3.get(task.category, 0) >= 2:
        factor *= 0.5

    # 同一任务今日第3次被抽中 -> 强烈降权
    if task.draw_count_today >= 3:
        factor *= 0.2

    return factor

冷却仅在当前抽卡会话中动态生效，不修改任务的持久化数据。
draw_count_today 字段在每次任务被抽中时递增，每日0点自动归零。

完整冷却规则：

冷却条件                           权重衰减系数    说明
同一任务连续出现（相邻两次抽卡）    0               直接移出候选池
同一类别（科目）连续出现           0.3             强烈避免重复感
同一类别在最近3抽中出现过2次       0.5             适度避免密集出现
同一任务今日第3次被抽中           0.2             避免同一任务被反复抽到


七、能量感知系统
======================================

7.1 设计理念
--------------------------------------

通过持续采集用户状态数据，建立动态的用户状态模型，实现任务与状态的智能匹配。
从"每隔5-30分钟随机询问"优化为"在关键交互节点采集"，避免打断用户专注流。


7.2 数据采集点
--------------------------------------

主要采集点（必须）：
- 任务完成后：弹出简单浮窗"刚才状态怎么样？"，1-10分滑块，可选填
  同时可选填心情1-10分，写入 task_completion_feedback
- 换牌/拒绝任务时：拒绝理由自动记录，间接反映当时状态

次要采集点（可选）：
- 每个时段结束时（上午、下午、晚间各一次），若用户该时段有活动记录，
  弹窗问"这个时段精力怎么样？"。用户可关闭不答。

不采集：
- 随机时间弹窗询问——避免打断番茄钟或专注状态

数据依然充足：主要采集点覆盖了每个任务的完成时刻和拒绝时刻，
一天至少能采集到数次有效数据，足以构建能量曲线。质量优于数量。


7.3 能量曲线生成
--------------------------------------

- 按小时聚合历史能量评分，计算每个时段的平均精力值
- 连续7天数据后开始生效，不足7天时使用默认值
- 每日更新，近14天数据权重更高


7.4 推荐逻辑调整
--------------------------------------

- 当前时段能量评分高 -> 优先推荐 energy_required 高的任务
- 当前时段能量评分低 -> 优先推荐 energy_required 低、resistance 低的任务
- 用户当日设为"低负荷日" -> 所有任务 energy_required 阈值下调2级


7.5 状态曲线模型
--------------------------------------

用户状态包含以下数据：
- energy_curve: 时间序列能量值
- task_preferences: 任务类型偏好
- rejection_reasons: 拒绝理由记录
- completion_history: 完成历史


八、用户状态与健康关怀
======================================

8.1 每日基调设置
--------------------------------------

四种模式：

模式        触发方式                    效果
高效日      用户主动选择                正常推荐，高难度任务权重 × 1.2
普通日      默认                        正常推荐（默认模式）
低负荷日    用户主动选择，或系统连续    仅推荐 energy_required ≤ 3 的任务
            3天能量低自动建议
休息日      用户主动选择                不推送任何任务，连续天数不计中断，
                                       不参与随机池

切换时机：
- 每日首次打开程序时弹窗询问"今天感觉怎么样？"，提供四个选项
- 用户不选择则默认普通日
- 选定后当日不再重复询问
- 次日再次弹窗

数据记录：
- 每日基调写入 user_state 表的 daily_tone 字段
- 用于后续分析和推荐策略调整


8.2 休息日的特殊处理
--------------------------------------

- 所有 daily_habit 任务今日免做，不计连续中断
- 所有随机池任务不参与抽取，抽卡界面显示"今日休息"状态
- 系统在休息日静默，主界面只显示"今日休息"和已完成的习惯追踪
- 不推送任何通知或提醒
- 次日自动恢复普通日模式，无需用户手动切换


8.3 低负荷模式
--------------------------------------

当系统检测到用户连续疲惫时（连续3天能量评分低于4分且未选择休息日）：
1. 弹窗建议："检测到你最近几天能量偏低，要不要切换到低负荷日模式？"
2. 用户确认后自动切换，当日所有任务 energy_required 阈值下调2级
3. 不强制，用户可以拒绝建议继续以普通日模式运行
4. 低负荷日模式下，抽卡界面展示的任务以短时间（<30分钟）、低精力需求为主


8.4 健康关怀机制
--------------------------------------

- 番茄钟休息提醒：工作25分钟后提醒休息5分钟
- 久坐提醒：超过1小时提醒活动
- 用眼提醒：连续使用屏幕后提醒休息眼睛


8.5 早睡守护机制
--------------------------------------

不参与抽卡，独立运行。只提醒，不强制。不剥夺用户熬夜的权利，但让用户意识到选择。

设置：
- 用户在设置中设定"目标睡觉时间"（如23:00）
- 数据记录在 user_state 表的 bed_time 字段

睡前1小时提醒：
- 到达目标睡觉时间前1小时（如22:00），弹出提醒：
  "距离目标睡觉时间还有1小时，不建议开始新任务。"
- 抽卡系统正常可用，但所有任务预估时间超过剩余时间的自动过滤
- 如果用户此时抽卡，卡面底部额外显示提示：
  "⚠️ 预计完成时间将超过你的睡觉时间"
  （仅当任务预估时间 > 距离睡觉时间时显示）

次日确认：
- 次日首次打开程序时，在每日基调弹窗之后，轻量询问：
  "昨晚大约几点睡的？"
- 提供三个选项：按时 / 稍晚 / 很晚
- 记录到 user_state 表的相关字段

正向激励：
- 连续按时早睡3天，主界面状态栏显示小星星图标
- sleep_early_streak 字段记录早睡连续天数
- 中断后重置为0


九、连续失败智能诊断
======================================

9.1 诊断触发条件
--------------------------------------

当某任务连续失败3次以上时触发诊断流程。


9.2 诊断选项
--------------------------------------

选项                    原因分析           系统响应
最近太忙/没时间         短期问题           降低任务频率
任务太难/不可能完成     任务设计问题       降低任务难度
白天想不起来/睡前堆积   推荐时机问题       调整推荐策略
任务拆分不够细          任务设计问题       AI辅助拆解
其他原因                待分析            记录详情


十、任务拆解与依赖
======================================

10.1 设计原则
--------------------------------------

- 系统负责拆解 - AI自动分析任务复杂度
- 用户确认执行 - 拆解结果需用户审核
- 忠实展示 - 不添加AI主观判断


10.2 拆解触发条件
--------------------------------------

1. 任务预估时间超过60分钟
2. 任务包含多个子目标
3. 用户主动请求拆解
4. 连续失败后AI建议拆解


10.3 拆解示例
--------------------------------------

原始任务：复习高数第七章

拆解结果：
1. 复习7.1节（20分钟）
2. 复习7.2节（20分钟）
3. 复习7.3节（20分钟）
4. 做7.1-7.3练习题（30分钟）

十四、任务类型说明
======================================

14.1 repeat_type 字段
--------------------------------------

值              说明        完成行为
single          单次任务    完成后彻底从数据库删除
daily           每日任务    完成后进入弃牌堆，每天自动重置
weekly          每周任务    完成后进入弃牌堆，每周自动重置
accumulation    积累型任务  完成后进入弃牌堆，需要手动抓回


14.2 任务分类策略
--------------------------------------

类型        示例              推荐策略
每日习惯    每天锻炼、早睡      daily，自动循环
每周任务    每周整理桌面       weekly，自动循环
弹性DDL    期末复习材料       accumulation，手动抓回
紧急任务    明天要交的作业      single，到期删除


14.3 任务分类的双维度模型
--------------------------------------

当前 repeat_type 只描述了"任务完成后怎么处理"，但任务在被抽取之前的行为策略同样需要分类。
建议引入第二个维度 task_profile，与 repeat_type 正交：

task_profile         含义                          抽卡策略特征
daily_habit         每日习惯                      不参与随机池，固定时段弹窗提醒；连续完成有正向反馈
weekly_routine       每周例行                      参与随机池但低权重；临近周末未完成则权重急剧上升
deadline_flexible   可压ddl                       前期权重极低；随ddl临近指数增长；ddl前最后两个可用时段进入强制推荐
deadline_progressive 需长期准备                    必须拆解为子任务；子任务均匀分布；设有每日最低推进线

两个维度独立运作：
- repeat_type 决定完成后的命运（删除/进弃牌堆/循环）
- task_profile 决定抽取策略的曲线形状（什么时候出现、以什么频率出现）

示例：一个"期末复习"任务，task_profile = deadline_progressive，
其子任务的 repeat_type = single（做完就消失，不循环）。


14.4 四类 task_profile 抽取策略详解
--------------------------------------

14.4.1 daily_habit（每日习惯）

行为特征：
- 不参与随机池，独立于抽卡系统运行
- 在用户设定的固定时段弹窗提醒（如锻炼在17:00，早睡提醒在睡前1小时）
- 抽卡界面不显示此类任务

完成状态管理：
- 每日0点自动重置完成状态，进入当天的待完成状态
- 记录连续完成天数
- 连续中断时显示历史最长记录作为参照

权重策略：不参与权重计算

界面表现：
- 在主界面独立区域显示今日习惯进度
- 习惯提醒以非侵入式弹窗展示
- 用户可点击"今日已完成"主动标记


14.4.2 weekly_routine（每周例行）

行为特征：
- 参与随机池，但动态权重，随周末临近逐步升高
- 每周一0点自动重置完成状态

权重策略（按天动态调整）：
  时间段            权重系数    说明
  周一至周四        0.3         低概率出现
  周五至周六        1.5         还没做就频繁出现
  周日              3.0         几乎必然被抽到

界面表现：
- 在任务卡片上标注"本周待办"标识
- 周日时特殊高亮显示


14.4.3 deadline_flexible（可压ddl）

行为特征：
- 权重随ddl临近指数增长
- ddl过后未完成则标记为逾期，移入特殊处理区

权重策略（按距ddl天数动态调整）：
  距ddl天数        权重系数    说明
  > 7天             0.5         安静待在池子里
  3-7天             1.0         权重线性升至1.0
  1-3天             1.5         权重升至1.5
  < 1天             2.5         权重升至2.5

强制推荐模式：
- 当用户可用时间块中仅剩2个合适时段时，触发强制推荐
- 下次抽卡必定出现该任务
- 界面显示"强烈推荐"标识

逾期处理：
- ddl过后自动标记为逾期（overdue）
- 移入特殊处理区，不再参与常规随机池
- 在任务管理界面以红色标注
- 用户需手动处理：延期/放弃/重新安排


14.4.4 deadline_progressive（需长期准备）

行为特征：
- 必须拆解为子任务，母任务本身不出现在抽卡池
- 子任务均匀分布在剩余天数中
- 子任务完成后自动从池中移除（repeat_type = single）
- 所有子任务完成时，母任务自动标记完成

最低推进线计算逻辑：
  每日应完成数 = 总子任务数 / 剩余天数（向上取整）

  示例：母任务"期末复习"拆解为15个子任务，
  剩余30天，每日应完成数 = 15/30 = 0.5
  -> 每2天至少完成1个

强制推送机制：
- 默认 min_push_time = 20:00
- 如果当天到 min_push_time 时，该做的子任务还没被抽到
- 系统绕过随机池，直接强制推送该子任务
- 强制推送在界面上显示"每日推进线"标识

顺延机制：
- 如果有子任务今日未完成，顺延到次日的最低推进线中
- 次日的最低推进线 = 当日应完成数 + 前日未完成数
- 连续3天未完成时，触发诊断流程

进度追踪：
- 主界面显示母任务的总体进度（已完成子任务数/总子任务数）
- 子任务列表展示每个子任务的ddl

十八、UI层设计
======================================

18.1 抽卡动画系统
--------------------------------------

卡背设计：
- 纯色底 + 简单几何图案（菱形或圆形排列）
- 四种 task_profile 对应四种卡背颜色：
  daily_habit：不参与抽卡，无需卡背
  weekly_routine：绿色
  deadline_flexible：蓝色
  deadline_progressive：红色（子任务也用红色，因为紧张感相同）
- 颜色饱和度偏低，不刺眼

单抽动画流程（总时长控制在1秒内）：
1. 用户点击"单抽"按钮，按钮短暂变为不可点击状态
2. 画面中央出现一张卡背，从下方滑入或淡入（0.3秒）
3. 卡背停留0.2秒后，执行翻转动画（0.4秒）：
   以卡片中央垂直轴为轴，卡背向右旋转消失，卡面从左旋转出现
4. 卡面完全展示，附带一个微弱的放大回弹效果（0.2秒）

五连抽动画流程：
1. 五张卡背从牌堆位置依次飞出，在画面中排成一行（0.6秒）
2. 用户可点击任意一张翻开
3. 点击后该卡翻转，其余卡片变半透明但仍可见
4. 用户可从五张中选择一张接受，或直接选择第一张

性能要求：
- 所有动画使用 Qt 内置动画框架，不引入额外依赖
- 帧率保持30fps即可，不需60fps
- 动画可被用户设置关闭

十九、任务依赖系统
======================================

19.1 核心理念
--------------------------------------

所有任务平等，不存在"母子任务"的层级概念。每个任务都是一张独立的卡片。

用户自由创建任务，自由设置任务之间的依赖关系。系统只负责：根据前置条件决定哪些卡进入抽卡池，根据任务类型决定抽卡时权重多少。


19.2 数据库字段
--------------------------------------

tasks 表新增两个字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| prerequisite_ids | TEXT | 前置任务ID列表，JSON数组格式，如 `[101,102,103]`。NULL或空数组表示无前置 |
| is_unlocked | INTEGER | 0=锁定（不在抽卡池），1=已解锁（可被抽取），由系统自动维护 |

新建任务时：若无前置则 is_unlocked=1；若有前置则 is_unlocked=0，等待所有前置完成后解锁。


19.3 解锁逻辑
--------------------------------------

任务完成/跳过时触发连锁检查：

1. 当前任务标记为完成（或跳过）
2. 查找所有 prerequisite_ids 包含此任务ID的其他任务
3. 对每个候选任务，检查其所有前置是否都已完成
4. 若全部完成，将该任务的 is_unlocked 置为1，进入抽卡池
5. 若存在新解锁任务，在主界面给轻提示："新任务已解锁：xxx"

跳过机制：用户可将任务标记为"跳过"，效果等同于完成——触发后续解锁，但不记录为"已完成"。


19.4 循环依赖检测
--------------------------------------

设置 prerequisite_ids 时，系统向上追溯前置链。若发现循环（A依赖B，B依赖A），拒绝保存并提示用户。


19.5 抽卡池过滤
--------------------------------------

抽卡时只返回同时满足以下条件的任务：
- is_unlocked = 1
- 不在弃牌堆
- 其他现有过滤条件（时间匹配等）

锁定的任务对用户完全隐形，不出现在抽卡界面、卡池查看、弃牌堆中。


19.6 依赖关系图视图
--------------------------------------

一个独立的可视化视图，展示所有任务之间的依赖连线。

功能：
- 以节点图形式展示所有任务及其依赖关系
- 节点颜色区分状态：绿色=已完成，蓝色=已解锁待抽取，灰色=锁定中
- 连线箭头表示依赖方向（A→B 表示B依赖A）
- 用户可拖拽节点调整布局
- 用户可直接在节点间拖拽连线来创建/删除依赖关系
- 点击节点跳转到该任务的详情

节点信息：
- 显示任务名称
- 若为锁定状态，小字显示"等待：xxx, xxx"


19.7 手动设置依赖
--------------------------------------

创建/编辑任务时，提供"前置任务"选择区：
- 从已有任务列表中多选
- 默认不选（无前置）
- 支持按标签筛选


19.8 与现有功能的关系
--------------------------------------

- deadline_progressive 任务的依赖完全由用户手动设置，系统不预设结构
- 最低推进线逻辑中，如果目标ddl任务本身被锁定，系统追溯到前置链上第一个已解锁但未完成的任务进行推送
- 冷却机制、权重计算、换牌规则均只作用于已解锁任务
- 标签系统、日程系统不受影响


19.9 典型使用场景
--------------------------------------

用户创建以下任务并设置依赖：

```
复习高数7.1节     — 无前置
复习高数7.2节     — 前置：复习高数7.1节
复习高数7.3节     — 前置：复习高数7.2节
做7.1课后题       — 前置：复习高数7.1节
做7.2课后题       — 前置：复习高数7.2节
做7.3课后题       — 前置：复习高数7.3节
整理7.1笔记       — 前置：复习高数7.1节
综合练习           — 前置：做7.1课后题, 做7.2课后题, 做7.3课后题
```

初始抽卡池只有"复习高数7.1节"。完成后，"复习高数7.2节""做7.1课后题""整理7.1笔记"同时解锁，池中出现三张可选卡片。用户根据当前精力和时间自主选择。


18.7 主界面微调
--------------------------------------

新增元素：
- 顶部状态栏：显示当日基调图标 + 今日已完成任务数 + 当前连续早睡天数
- 抽卡按钮下方显示"今日换牌机会：1次"的小字提示（用过后显示"已使用"）
- 弃牌堆按钮增加小红点，提示"有N张卡在弃牌堆"

设计原则：原有按钮保持不变，仅增加这些状态提示。


十九、新增功能模块
======================================

19.1 早睡守护
--------------------------------------

已在 8.5 节详细描述。独立于抽卡系统运行，核心机制：

设置：用户设定目标睡觉时间
提醒：睡前1小时弹窗提醒
过滤：预估超过剩余时间的任务不进入抽卡池
卡面提示：超出睡觉时间的任务显示警告
次日确认：询问实际入睡时间
激励：连续3天早睡显示小星星图标


19.2 最低推进线守护
--------------------------------------

仅对 deadline_progressive 子任务生效。

计算逻辑：
- 母任务设定ddl和总子任务数
- 系统每日0点计算：剩余子任务数 / 剩余天数 = 今日最低完成数（向上取整）
- 该数值存储在内存中，今日有效

触发时机：
- 用户在 min_push_time（默认20:00，可配置）之后打开抽卡界面
- 系统检查今日该母任务的子任务是否已完成最低数

如果未完成：
- 随机池暂停，直接推送一个未完成的子任务
- 卡面顶部显示红色横幅："⏰ 今日必须完成（进度：1/3）"
- 该次抽卡不可换牌
- 该次推送不消耗每日换牌机会

如果已完成最低数：
- 正常随机池继续运作
- 该母任务的剩余子任务仍可被抽到，但不再强制

用户可见的进度指示：
- 在任务卡片上显示"今日进度：2/3"
- 母任务详情页显示总进度条和每日完成趋势
